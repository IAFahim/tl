# KindSystems

K2 benchmarks through the generated path (issue #555, plan #552 section 4.12). The domain (`Domain.cs`) is script-generated by `gen.py`: 62 span kinds (`K0`..`K61`, each with a feeder consumer), the pulse kind `Dmg`, one kind system `KSys`, and a legacy twin (`Legacy` in its own system `LSys`) that runs plan 1's per-entity kernel as the baseline. `Generated/TlSystemsKindBench.g.cs` is the committed emitter snapshot (`TL_UPDATE_BENCH=1` with `KindBenchGenTests`). Libraries are baked from the built assembly and not committed.

```sh
benchmarks/KindSystems/bake.sh
dotnet build benchmarks/KindSystems/KindSystems.csproj -c Release
dotnet run --project benchmarks/KindSystems/KindSystems.csproj -c Release --no-build -- --smoke
dotnet run --project benchmarks/KindSystems/KindSystems.csproj -c Release --no-build -- --filter '*' --artifacts benchmarks/KindSystems/results/k2
```

`KindSystems.Aot` publishes the same scenario as a NativeAOT binary: 600 steps of kinds against the legacy kernel with bullet pulses, bit-equal at every step.

## Verdict (i9-14900K, .NET 10, 100,000 entities, 32 steps per op, BenchmarkDotNet medians in `results/k2`)

| Gate | Shape | Measured | Target | Result |
|---|---|---|---|---|
| K-A | one walk entry per entity, `Tick` + `Run` vs plan 1 `Advance` + `Run` | 31.09 vs 33.88 ms = 0.92x | <= 1.2x | pass |
| K-B | same, 10% of entities playing | 3.40 ms = 0.11x of K-A | <= 0.15x | pass |
| K-C | 100 timelines, staggered ticks | 35.04 ms = 1.13x of K-A | <= 1.3x | pass |
| K-D | `Tick` alone, no boundary events | 7.52 ms / 3.2M playbacks = 2.35 ns, 0.24x of K-A | <= 0.5x of K-A (amended on #552) | pass |
| K-E | 63 kinds defined, 2 reachable per entity, 31 timelines each arm, entities grouped by kind set | storage 48 B per entity (2 kinds); time 97.5 vs 76.2 ms = 1.28x | storage 2 kinds only; time <= 1.1x | storage pass, time miss |
| K-F | 8 game damage pulses per entity vs 1, `Dmg` with `FoldsPulses` and sent through `Pulses<int, DmgFold>` (#562, `results/k2b`) | (71.2 - 27.8 ms) / (7 x 3.2M) = 1.9 ns per extra pulse; without folding 6.9 ns (`results/k2`) | <= 3 ns per extra pulse with folding (amended on #552) | pass |
| Allocation | warm steps, 20 operations per shape | 0 B (`results/k2/smoke.txt`); NativeAOT binary 0 B over 100 steps | 0 B | pass |
| Parity | kinds vs the legacy kernel | bit-equal after every step (`--smoke`, `KindSystems.Aot`, `KindRunTests`) | exact | pass |

Why the misses (K-E remains; K-F is fixed by folding):
- K-E: the 62-kind arm touches 62 distinct kind loops and feeder bodies per step, the 2-kind arm touches 2, so its hot code and library tables are about 30 times larger. The storage claim holds exactly; the time ratio measures instruction and table footprint, not the kind count.
- K-F: without folding, each pulse is written to the send queue, read at merge, written to the owner's entries and read by the kind loop, about 40 bytes of traffic per pulse, and the 100,000-row kind table no longer fits in L2. Declaring `gamePulses` in `library.json` removes the heap spill (overflows 0) but not the traffic. `FoldsPulses = true` on a Combine kind lets game code send through `Pulses<T, TFold>`, which folds a pulse into the previous one when it has the same target (one entry per run of pulses). It changes float sums because the order of additions changes, so it is opt-in per kind and the kind must be baked with the flag; integer kinds are bit-identical.

## Kind groups (issue #564, `results/k10`)

`TL_GROUP=Pool python3 gen.py` puts the 62 span kinds in one kind group; `TL_UPDATE_BENCH=1` with `KindBenchGenTests` and `bake.sh` then rebuild the generated snapshot and libraries for that variant (run the same steps without the variable to restore). Smoke runs, 100,000 entities, 32 steps, same CPU:

| Shape | Ungrouped | One group of 62 | Why |
|---|---|---|---|
| K-A, one walk entry per entity | 31.3 ms | 367 ms | every member's loop scans all rows of the shared table and skips other kinds' entries |
| K-E, 2 of 62 reachable | 78.3 / 97.1 ms | 468 / 485 ms | same |
| Storage, 2 reachable kinds | 48 B | 76 B | one header, but the group capacity is sized for the worst case of the whole group (5 x 12 B) |
| Parity with plan 1 | bit-equal | bit-equal | |

Groups trade time and some inline storage for fewer headers, so they pay off for entities that would reach dozens of rarely used kinds (plan section 2, K10), not for a few hot kinds. Rows are shared, so the `Enabled` and `Active` bits belong to the group, not to a member kind.
