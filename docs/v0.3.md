# v0.3 — region-stable materialization

**Status: implemented.** This document records the v0.3 API delta and the
engine rework that pairs with it, mirrored from the benchmarks sandbox where
the design landed first (commits `3e8632a..7d1f30c`; `benchmarks/Hooks.cs` is
the reference). Version 0.2.0 → 0.3.0 in `Tl.Runtime`. Additive: no v0.2
signature changes.

## 1. The change in one paragraph

v0.2's `Tracks` view walked the authored track/clip rows on every tick and
carried the whole table bundle in the enumerator; blends were resolved
eagerly in `MoveNext`, and there was no way to address one work directly.
v0.3 uses the one fact the tables encode — the active work set is constant
inside a region — to materialize that set **once, at build time**: one
internal `WorkSlot` per track row, with payload-map hops resolved, blend
windows captured, and the outer-window entry-reference edges (`EnterF`/
`EnterB`) precomputed. A region's per-tick view is then just
`workSlots.Slice(row.TrackStart, row.TrackCount)`, and `Tracks` becomes a
thin carrier with first-class indexing; `TrackWork` becomes a small view of
ONE slot instead of a copy of the bundle. Blends resolve lazily into the
blend scratch on first `Clip` read, so works the consumer never visits are
never blended.

## 2. API delta table

| v0.2 | v0.3 |
| --- | --- |
| `Tracks<TTrack, TClip>.Count` + `GetEnumerator()` only | unchanged, plus `this[int]` (a `TrackWork` view of one work, bounds-checked by the span) and `Slice(int start, int length)` (zero-copy sub-view, bounds-checked) |
| `Tracks.Enumerator` copies the table bundle per iteration (`TrackRow`/`ClipRow`/payload map/edges/scratch) | flat walk over the slot span; `Current` is a thin view of one slot |
| `TrackWork.Clip` reads eager blend results written by `MoveNext` | lazy: the `Clip` getter blends into the region-local scratch ordinal on first read |
| `TrackWork.State` recomputes window edges from `ClipRow`/`ClipEdge` per read | one compare against the slot's `EnterF`/`EnterB` entry references |

Everything else is unchanged: `IBlend`, the `IForward`/`IBackward` callback
signatures, `Playback`, `Cursor`, the registry and lifecycle calls, the
authoring builder, `TimelineOptions`, and the `ITrackTables` generation
contract (the slot table is **derived**, not authored — `GeneratedTimeline`
builds it once into a per-closure static cache).

`WorkSlot` and `MaterializeWorkSlots` are internal on purpose: the slot
encoding is an engine implementation detail; the public promise is the
indexed/sliced view surface and its parity with enumeration.

## 3. The engine rework

- **Build-time materialization.** `TimelineCompiler.Compile` runs
  `PlaybackCore.MaterializeWorkSlots` after storage dedup (aliased row runs
  share aliased slots; identical runs yield identical region-local blend
  ordinals, so the pass is idempotent), and the registry entry carries the
  table. The generated-table shell computes the same table once per
  closure. Never per tick, and never per call: a first sandbox cut
  re-materialized the slots on region entry **per call** and measured
  +8 ns/tick on a non-consuming callback — single-tick calls are a region
  entry every time (see `docs/benchmarks.md`, v0.3 section).
- **Blend scratch ordinals are dense per region**, assigned in slot order,
  matching the existing `MaxActiveBlends` scratch sizing; standalone clips
  never take scratch.
- **Movement facts pack into one flag byte** (`MovementSpan`: direction,
  enter-possible gate, crossed-always), so the per-tick handoff is a single
  store; the per-work `State` test reduces to one prev-compare against the
  slot's entry references for works active at the destination (activity
  pins `Start <= tick < End`). The src engine does not emit the sandbox's
  prefix-count `CutCounts` table (that experiment's verdict was REJECT), so
  the enter gate is always open — the flag keeps the view honest either way.
- **Dispatch unchanged.** The src engine's managed-byref typed-pointer
  bridges (`Run`/`ScratchRun` delegate pointers carrying `in TInput`/
  `ref TResult` directly) needed no rehydration tricks: materialization
  only adds one more typed span — `entry.WorkSlots.AsSpan()` — to the
  fetches each bridge already performs, replacing the track-row, clip-row,
  edge and payload-map spans the runtime no longer reads.
